## 结论摘要

OlympusHive 的行为更像 event-level 篮子策略，而不是单笔 trade-level 策略。

核心特征：

- 同一城市、同一天、同一最高温市场，会同时买多个温度档位。
- 仓位有主次：一个或两个主档位放较大金额，旁边低价档位用小仓补赔率弹性。
- 低价高倍仓很重要，金额可能小，但对最终收益分布影响很大。
- 他会动态卖出、转向或保留残余尾仓，所以旧挂单不能脱离 event 状态长期存在。

我们当前系统的问题：

- 以单笔成交为核心，容易漏掉同 event 的其他档位。
- 某个 outcome 已有挂单时，后续同 outcome 的补仓会被“全局已有挂单”挡住，导致仓位不足。
- FOK 未吃到且 post-only 挂单失败时，很多单子没有形成有效 pending order，日志表现为“未成功挂单，TTL 未生效”。
- 低价篮子里，员工已经形成组合，我们只买到其中一小块，收益结构被破坏。
- 如果旧高价挂单后来回撤成交，而低价新方向没跟上，会形成双重损失。

## 对改造方向的支持

数据支持 event-level 改造，而不是继续 trade-level 小补丁。

建议方向：

1. 同一 event 建篮子
   - 按 city + 日期 + 高/低温 + event slug 聚合。
   - 短时间内同 event 多 outcome BUY，应进入同一个策略篮子。

2. 低价篮子优先级提高
   - 低价高倍小仓不应因为单笔金额小或挂单失败而消失。
   - 可设 event-level 最小补仓：当同 event 总目标达到阈值，低价 outcome 可以合并补足。

3. 挂单要绑定 event 状态
   - 员工转向其他 outcome 后，旧 outcome 的补买挂单应降级、缩量或取消。
   - 挂单不能只按单笔 TTL 判断，要看同 event 最新篮子。

4. 允许同 outcome 补足挂单
   - “同 outcome 只允许一个 BUY 挂单”会导致补仓被挡住。
   - 应允许更新/替换/合并挂单，使挂单金额接近当前目标。

5. 未成功挂单要进入待补队列
   - “未成功挂单，TTL 未生效”不应等于结束。
   - 应记录为 `missed_intent`，后续 event-level reconcile 继续尝试补齐或取消。

6. 仓位配比改成 event budget
   - 单 outcome 50U cap 还不够。
   - 应有 event 总预算，再在 outcome 间按员工权重、价格区间、赔率弹性分配。

## 暂定结论

OlympusHive 的优势可能不是单笔命中，而是对天气 event 做多档位组合、主仓和低价尾仓搭配、及时止盈/轮动。

我们的系统当前最大问题是：把组合策略拆成孤立成交处理，导致低价尾仓漏掉，高价或过时挂单反而可能成交。

下一版核心应是 event-level copy trading：先保留策略篮子形状，再谈 50% 跟单和 50U cap。
