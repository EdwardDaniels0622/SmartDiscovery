# OlympusHive 事件篮子跟单改造计划

## 1. 背景

最近实际 API 复盘显示，OlympusHive 在天气市场里的核心行为不是简单逐笔下注，而是围绕同一个城市同一天的多个温度选项构建事件篮子。

典型现象：

- 同一 event 内买多个 outcome，例如 Seoul、NYC、Chicago 都出现多温度档组合。
- 错误温度档也可能通过盘中波动提前卖出赚钱。
- 低价腿不是装饰，漏掉后我方收益结构会和员工明显分叉。
- 300-400U 启动资金无法机械按 50% 复制员工每笔金额。
- 旧挂单如果不随事件篮子变化撤销，可能在机会已经变化后被回撤成交，形成坏仓位。

因此，下一版不应继续使用“每笔 50% 金额 + 单 outcome 50U 上限”作为主策略，而应改为：

```text
实时热路径快速小买
  + 事件级目标账本
  + 价格/金额分档
  + 后续篮子修正
  + 源仓位对账降级为校准来源
```

## 2. 总目标

在不牺牲实时速度的前提下，尽量复制 OlympusHive 的事件篮子形状，而不是复制单笔成交金额。

目标：

- BUY 仍以 `/activity` 实时成交为主，员工买入后立即尝试小额跟进。
- 后续根据同 event 累计买入结构，逐步修正我方目标仓位。
- 对低价腿、小额腿保持敏感，避免漏掉赔率结构。
- 对高价、低利润、大额单降低资金占用。
- 源仓位对账只负责校准目标和发现漏单，不直接绕过实时跟单逻辑下单。
- 多员工、全局 outcome cap、手动 outcome 接管继续生效。

非目标：

- 初版不追求完美复刻员工真实仓位。
- 初版不做城市永久黑白名单。
- 初版不做复杂机器学习或收益预测。
- 初版不自动扩大总本金风险。

## 3. 系统边界必须理清

当前系统至少有两条不同职责链路。

### 3.1 跟单系统

跟单系统是实时执行层，主要输入是 `/activity`。

职责：

- 发现员工最新 BUY/SELL。
- 判断这笔成交是否属于可跟事件。
- 立即执行小额 BUY、SELL、撤单或挂单。
- 维护事件级本地目标账本。
- 处理 pending order 成交、失败、过期和重挂。

特点：

- 速度优先。
- 以员工真实成交价和成交时间为准。
- 允许先不完美，但要先拿到关键低价/主仓入场机会。

### 3.2 源仓位对账

源仓位对账是校准层，主要输入是员工 `/positions`。

职责：

- 周期性确认员工当前是否仍持有某 outcome。
- 发现 `/activity` 漏掉的累计持仓变化。
- 更新员工目标账本。
- 发现本地账本明显偏离时发出修正建议或低优先级补漏。

禁止：

- 不允许源仓位对账直接市价清仓。
- 不允许源仓位对账绕过全局 cap 补仓。
- 不允许源仓位对账用旧均价抬价重挂。
- 不允许源仓位对账在手动接管 outcome 上做任何交易动作。
- 不允许源仓位对账和实时跟单抢执行权。

一句话：

```text
/activity 决定实时动作；/positions 只负责校准和补漏。
```

## 4. 新核心概念

### 4.1 Event Basket Key

事件篮子按城市日期 event 归类：

```text
event_key = source_name + ":" + event_slug
```

例如：

```text
OlympusHive:highest-temperature-in-seoul-on-july-14-2026
```

同一个 event 下可以有多个 exact outcome：

```text
29C Yes
32C Yes
33C Yes
34C Yes
```

### 4.2 Outcome Key

真实交易和全局风控仍绑定 exact outcome：

```text
position_key = condition_id + ":" + asset
```

事件篮子负责“策略形状”，outcome key 负责“真实仓位和订单”。

### 4.3 员工事件账本

每个员工、每个 event 维护：

- 员工每个 outcome 的累计 BUY 金额。
- 员工每个 outcome 的累计 SELL 金额。
- 员工每个 outcome 的净目标金额。
- 员工每个 outcome 的加权平均买入价。
- 最近 BUY/SELL 时间。
- 事件是否已形成多腿篮子。

### 4.4 我方事件目标

每个 event 有一个总预算，再分配到多个 outcome：

```text
event_budget_usd
outcome_target_usd
```

但初版不是等篮子完整后才买，而是：

```text
第一笔先按热路径买
后续再用事件目标账本修正
```

## 5. 资金约束

当前启动资金按 300-400U 设计。

建议初版资金框架：

| 项目 | 建议 |
|---|---:|
| 总本金 | 300-400U |
| 最大活跃敞口 | 200-280U |
| 现金预留 | 80-120U |
| 普通单事件预算 | 12-18U |
| 强信号单事件预算 | 25-35U |
| 极强临时事件预算 | 40-45U |
| 单 exact outcome 默认上限 | 50U 继续保留 |

注意：

- `50U` 是单 exact outcome 保护上限，不代表每个事件都应打到 50U。
- 事件预算应优先限制总体资金占用。
- 现金预留是为了后续新事件和篮子低价腿，不应被第一批高价单吃光。

## 6. BUY 规则

### 6.1 热路径：第一笔快速入场

员工 BUY 到来时，不等待完整篮子判断，先按价格和员工金额给一个小额初始仓位。

初始仓位定位：

```text
先拿到票，不一次性买满目标。
```

建议价格分档：

| 员工买入价 | 含义 | 我方基础初始买入 |
|---|---|---:|
| 0-10c | 低价高倍腿 | 1U |
| 10-30c | 机会腿 | 1-2U |
| 30-60c | 主力判断区 | 2-3U |
| 60-85c | 偏确定但利润下降 | 1-2U |
| 85-95c | 高价低利润 | 1U |
| 95-98c | 极低利润 | 0-1U 或只提醒 |
| >98c | 几乎无利润 | 不跟 |

### 6.2 员工金额加权

员工出手金额只做放大因子，不再直接 50% 复制。

建议初版：

| 员工短时间累计买入 | 倍数 |
|---|---:|
| <5U | 1.0x |
| 5-20U | 1.5x |
| 20-80U | 2.0x |
| 80U+ | 3.0x |

最终初始买入：

```text
initial_buy = price_bucket_base * source_notional_multiplier
```

再受这些限制：

- 不超过事件预算剩余额度。
- 不超过单 outcome 全局 cap 剩余额度。
- 不超过当前可用余额安全比例。
- 不超过热路径单笔最大值，例如 5-8U。

### 6.3 小额单不跳过

员工小额成交可能是挂单被吃，也是低价腿形成方式。

规则：

- 不因员工买入金额低于 1U 直接跳过。
- 低价腿可以触发 1U 最小跟单或 1U 挂单。
- 对非低价腿，可以先累计意图，目标达到 1U 后执行。

## 7. 事件篮子修正规则

### 7.1 修正触发

以下情况触发事件篮子重算：

- 同 event 新 BUY。
- 同 event 新 SELL。
- pending BUY 成交或取消。
- 源仓位对账发现员工持仓明显变化。
- 定时短周期，例如 5-15 秒。

### 7.2 目标分配

对一个 event，先计算员工净买入结构：

```text
source_outcome_weight = source_outcome_net_buy_usd / source_event_net_buy_usd
```

再计算我方目标：

```text
our_outcome_target = event_budget_usd * source_outcome_weight
```

低于 1U 的低价腿可以补到 1U，但必须仍受事件预算和现金约束。

### 7.3 买少了怎么办

如果我方低于目标：

1. 优先补员工仍在继续买的 outcome。
2. 其次补事件篮子中的低价腿。
3. 价格偏离员工均价不大时可以吃单。
4. 价格偏离明显时只挂单，TTL 短。
5. 如果事件预算已用完，不为单个 outcome 强行突破。

### 7.4 买多了怎么办

如果我方超过目标，不立刻机械卖出。

| 超配程度 | 处理 |
|---|---|
| 轻微超配，超过目标 20-30% | 停止继续买该 outcome |
| 明显超配，但员工未卖 | 挂保护卖单，慢慢降回目标 |
| 严重超配，或员工开始卖 | 立即减仓，必要时市价或接近市价卖 |

原则：

- 买少可以补，买多处理成本高，所以第一笔必须偏保守。
- 不因为一次篮子重算就频繁买卖来回摩擦。

## 8. SELL 规则

SELL 必须快，但不能无脑清仓。

### 8.1 单 outcome 小比例 SELL

如果员工只是小比例卖出某个 outcome：

- 取消该 outcome 未成交 BUY。
- 按员工减仓比例同步降低我方该 outcome 目标。
- 如果需要卖出，优先挂保护卖单。
- 保护卖单价格可比当前可成交价低一定比例，例如 10-15%，但不能低到无意义。

### 8.2 大比例 SELL

如果员工大比例卖出某 outcome：

- 立即取消同 outcome 买单。
- 快速卖出我方对应超额仓位。
- 如果 FOK 失败，可以转为保护 GTC，并记录 pending exit。

### 8.3 事件级退出

如果同 event 多个 outcome 连续 SELL：

- 视为事件重心迁移或退出。
- 取消该 event 所有未成交 BUY。
- 重算整个 event 目标。
- 只保留员工仍支持的 outcome。

## 9. 挂单规则

挂单必须从单 outcome 视角升级到 event 视角。

### 9.1 挂单创建

允许挂单的情况：

- 价格偏离员工成交价，直接追价不划算。
- 低价腿当前卖一不足或 FOK 失败。
- 小额腿需要凑够最小订单。

挂单必须记录：

- event_key
- position_key
- trigger_trade_id 或 source_trade 时间
- 触发价格
- 我方限价
- 所属事件预算
- 创建时员工篮子快照

### 9.2 挂单撤销

以下情况应撤单：

- 员工 SELL 同 outcome。
- 同 event 员工重心迁移，旧 outcome 不再被篮子支持。
- 事件预算被其他更优 outcome 用完。
- 价格过期，TTL 到期。
- 用户手动接管 outcome。
- 源仓位对账显示员工已不持有且没有近期 BUY 支持。

关键原则：

```text
旧挂单不能独立存活，必须依附当前事件篮子。
```

## 10. 源仓位对账改造

### 10.1 频率

建议降低 `/positions` 频率：

- 正常：10-30 分钟一次完整对账。
- 发现 activity 降级或网络恢复后：补偿性对账一次。
- 某 event 活跃交易中：可以只对该员工该 event 做轻量校准。

理由：

- `/activity` 才是实时主链路。
- 高频 `/positions` 容易慢、容易缺失、容易和实时跟单抢逻辑。

### 10.2 对账允许做什么

允许：

- 更新员工 outcome 目标。
- 标记员工已经不持有某 outcome。
- 发现 activity 漏单后，创建低优先级补漏意图。
- 帮助撤销没有源支持的旧挂单。
- 帮助清理过期或无效本地状态。

### 10.3 对账禁止做什么

禁止：

- 直接市价卖出我方仓位。
- 直接追价买入。
- 在没有明确 BUY activity 的情况下抬高挂单价格。
- 对手动接管 outcome 做交易动作。
- 单独决定事件篮子，只能辅助实时 activity 账本。

### 10.4 源仓位缺失处理

`/positions` 缺失不能立刻等于员工卖出。

处理建议：

1. 如果该 outcome 从未在 source positions 中确认过，不允许对账清仓。
2. 如果刚有近期 BUY，延长缺失观察期。
3. 连续多次缺失且无近期 BUY/SELL，再降低该员工目标。
4. 即使降低目标，也通过全局协调层决定是否卖出，不直接清仓。

## 11. 多员工和手动接管兼容

本改造必须继承 `multi_employee_autocopy_coordination_plan.md` 的原则。

### 11.1 多员工

- 每个员工有自己的 event basket。
- 同一个 exact outcome 的真实钱包目标仍走全局汇总。
- 一个员工卖出，只降低该员工贡献。
- 其他员工仍支持时，不误卖全局仓位。

### 11.2 手动接管

手动接管仍绑定 exact outcome：

```text
condition_id + asset
```

手动接管后：

- 不自动买。
- 不自动卖。
- 不源仓位对账补挂。
- 不退出重试。
- 不因为 event basket 修正重新挂单。

## 12. Telegram 提示改造

提示要能解释系统为什么这么做。

BUY 提示应包含：

- 热路径还是篮子补仓。
- 员工买入金额和价格。
- 我方本次金额。
- event 已用预算 / 总预算。
- outcome 已承诺 / outcome cap。
- 是否因为价格分档、员工金额倍数、事件预算而裁剪。

SELL 提示应包含：

- 员工是小比例减仓、大比例减仓，还是事件级退出。
- 我方卖出比例和原因。
- 是否有保护挂单。
- 是否取消了同 event 其他旧 BUY。

挂单提示应包含：

- 当前盘口价。
- 我方挂单价。
- 员工原成交价。
- 挂单属于哪个 event basket。
- TTL 和过期条件。

源仓位对账提示应明确标记：

```text
来源：源仓位对账，仅更新目标/补漏建议，不是实时成交信号。
```

## 13. 分阶段实施计划

### 阶段 0：只加统计和影子账本

目标：不改变实盘行为，先验证事件篮子账本是否能正确还原 OlympusHive。

改动：

- 从 `/activity` 构建 event basket ledger。
- Telegram 或日志输出 event basket summary。
- 记录每个 event 的员工 outcome 权重。
- 记录按新规则会产生的目标仓位，但不下单。

验证：

- 对比 `docs/olympushive_city_day_outcome_breakdown.md`。
- 确认同 event 多 outcome 能正确归组。
- 确认小额低价腿不会被账本漏掉。

### 阶段 1：热路径 BUY 改成价格/金额分档

目标：替代机械 50% 跟单。

改动：

- 新增价格分档基础金额。
- 新增员工短时间累计买入倍数。
- 新增热路径单笔上限。
- 继续受全局 outcome cap 和手动接管限制。

验证：

- 单元测试覆盖各价格档。
- 单元测试覆盖 0.1U、0.5U 等小额成交。
- 单元测试覆盖 >98c 不跟。
- 回放 OlympusHive 最近 5 天数据，比较新旧目标差异。

### 阶段 2：事件预算和篮子补仓

目标：同 event 多 outcome 不再漏腿。

改动：

- 每个 event 建预算。
- 根据员工累计结构计算我方 outcome target。
- 买少了补仓或挂单。
- 买多了停买或保护卖。

验证：

- Seoul July 14、NYC July 14、Chicago July 15 回放。
- 确认低价腿至少形成最小有效仓位。
- 确认单 event 不突破预算。

### 阶段 3：挂单事件化

目标：避免旧挂单变成坏仓位。

改动：

- pending BUY 增加 event basket 归属。
- 同 event 重心迁移时撤销旧挂单。
- TTL 和撤单原因写入提示。

验证：

- 员工从 30C 转向 31C/32C 时，30C 旧挂单被撤或降级。
- 用户手动取消后不再自动补挂。
- 源仓位对账不能抬价重挂。

### 阶段 4：SELL 按比例和事件退出

目标：卖出响应更快，同时避免小卖出导致误清仓。

改动：

- 小比例 SELL 同 outcome 比例减仓。
- 大比例 SELL 快速减仓。
- 同 event 多 outcome 连续 SELL 触发事件级退出。
- FOK 失败后记录 pending protective exit。

验证：

- 员工小卖 1U 不触发全清。
- 员工清掉主仓时我方快速退出。
- pending exit 返回 GTC 时上层正确记录。

### 阶段 5：源仓位对账降频和补偿

目标：让 `/positions` 服务于校准，不干扰实时跟单。

改动：

- 完整 source positions 对账降到 10-30 分钟。
- 网络恢复后做一次补偿对账。
- 对账只更新目标和补漏意图。
- 对账缺失不直接清仓。

验证：

- `/positions` 缺失不会误卖。
- activity 漏单后能发现目标偏差。
- 多员工同 outcome 不被单员工对账误伤。

## 17. 当前建议

先不要直接把完整事件篮子策略上实盘。

推荐顺序：

1. 先做阶段 0 影子账本和回放。
2. 确认新规则在 OlympusHive 最近 5 天数据上不会明显过仓。
3. 再实装阶段 1 的热路径 BUY。
4. 最后逐步打开事件补仓、挂单事件化和 SELL 改造。

这样可以保留速度，也避免一次性把跟单系统和源仓位对账都改乱。

  - 记录每个 outcome 的 BUY/SELL 金额、份额、平均买入价和最近动作。
- BUY 热路径支持事件策略：
  - 第一腿先按价格档和员工累计金额小额进入。
  - 同 event 达到多个 outcome 后，按事件预算和 outcome 权重重算目标。
  - 事件预算会裁剪目标，不只裁剪本次下单金额。
  - 策略目标大于 0 但低于交易所最低 5 份/1U 约束时，会抬到最低可下单金额，并在原因里说明。
- 源仓位对账保护：
  - 策略启用且配置关闭时，`/positions` 不直接补买。
  - 策略启用且配置关闭时，`/positions` 不直接清仓。
  - 对账只作为目标校准/补漏线索，实时动作仍由 `/activity` 驱动。
- OlympusHive 启动脚本模板已指定策略配置路径，但没有重启服务。
